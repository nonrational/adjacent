# PR #75 — Scaffold a default adjacent.toml in `adj add`

> **Rust lesson:** When a config file is meant for a *human* to open and edit, hand-render it as text so comments, `# TODO` placeholders, and commented-out optional fields survive — `toml::to_string(&struct)` would drop every one of them — and write it with `std::fs::write` behind a `!path.exists()` guard so you never clobber a file the user already owns.
> **Tags:** `std::fs` · `toml` · `file-generation`
> **Merged:** 2026-06-21 · +1552/−6 · [View PR](https://github.com/nonrational/adjacent/pull/75)

## The situation

`adj add .` used to dead-end when a directory had no `adjacent.toml`. This PR makes it
*generate* a sensible default instead — filling in `name` and `cmd` when it can detect
the stack, leaving `# TODO` guidance when it can't. The generated file's whole reason
for existing is that a person opens it next and edits it. So two questions: how do you
produce a config file that's friendly to a human editor, and how do you write it to disk
without ever overwriting one the user already wrote?

## The Rust idea

Rust's `toml` crate can serialize a struct straight to a config string —
`toml::to_string(&cfg)` — the write-side mirror of the `#[derive(Deserialize)]` that
reads `adjacent.toml` back in (PR #19). It's the obvious reach, and for a machine-to-machine
file it's the right one: faithful, round-trippable, no hand-maintained text.

But `to_string` serializes **data**, and a struct holds no comments. Feed it an
`AppConfig` and you get back exactly:

```toml
name = "myapp"
cmd = "npm run dev"
```

No header explaining where the file came from. No `# Optional:` block showing the
fields the user *could* set. No `# TODO` next to a value they still need to fill in.
For a scaffold, those comments aren't decoration — they're the entire payload. The file
is a teaching aid disguised as config.

So the tool for a human-facing config file is the opposite of a serializer: you
**render the text by hand**, comments and all, and treat the struct as something you'll
parse the result *back* into later, not something you serialize *from*. The cost is that
you're now responsible for producing valid TOML yourself — which the PR pins down with a
test, below.

## In this PR

`render` builds the file as a string. Every line the user benefits from — the header,
the `# TODO`s, the commented-out optional block — is text serde would never emit:

```rust
// crates/adj/src/scaffold.rs
fn render(name: Option<&str>, cmd: Option<&str>) -> String {
    let name_line = match name {
        Some(n) => format!("name = \"{n}\"\n"),
        None => "name = \"app\"  # TODO: set a name (lowercase letters, digits, `-`)\n".to_string(),
    };
    let cmd_line = match cmd {
        Some(c) => format!("cmd = \"{c}\"\n"),
        None => "cmd = \"\"  # TODO: set your dev command, e.g. \"npm run dev\"\n".to_string(),
    };
    format!(
        "# Generated by `adj add` — edit and re-run if needed.\n\
         {name_line}\
         {cmd_line}\
         \n\
         # Optional:\n\
         # port_env = \"PORT\"\n\
         # env_file = \".env.local\"\n\
         # idle_timeout = \"15m\"          # \"30s\" / \"1h\" / \"off\"\n\
         # health_check_url = \"/healthz\"\n"
    )
}
```

The `match name` / `match cmd` is where "known value" and "placeholder with guidance"
branch: a detected value renders as a live `name = "…"` line, an absent one renders as a
commented `# TODO`. A serializer can't express that — there's no struct field that means
"leave a note for the human here."

Hand-rendering does put one job on you: emitting *valid* TOML. The PR's doc comment spells
out why this particular template is safe without any escaping logic —

```rust
// crates/adj/src/scaffold.rs
/// Render the `adjacent.toml` body. `None` fields become TODO placeholders. Detected commands
/// come from a fixed vocabulary (none contain `"`) and `sanitize_name` guarantees `name` is
/// `[a-z0-9-]`, so no TOML string escaping is needed here.
```

— and a unit test nails the door shut by parsing the rendered string back through the real
`toml` crate. If a future edit ever produces something that isn't valid TOML, this goes red:

```rust
// crates/adj/src/scaffold.rs
assert!(
    toml::from_str::<toml::Value>(&toml).is_ok(),
    "invalid toml: {toml}"
);
```

That's the safety net that makes hand-rendering defensible: you give up serde's
guaranteed-valid output, so you buy it back with a round-trip assertion.

Then the write, in `client::add`. The whole thing is guarded on the file *not* already
existing:

```rust
// crates/adj/src/client.rs
let manifest = canon.join("adjacent.toml");
if !manifest.exists() {
    let scaffold = scaffold::build(&canon);
    std::fs::write(&manifest, &scaffold.toml)
        .with_context(|| format!("writing {}", manifest.display()))?;
    // ... branch on detected name/cmd ...
}
```

`std::fs::write` is the one-liner form — open (creating or truncating), write the whole
buffer, close, all in a call. The `if !manifest.exists()` in front of it is the
not-clobbering rule: a user who already hand-wrote an `adjacent.toml` never has it
silently replaced by a generated one. (An integration test asserts exactly this — an
existing manifest comes back byte-identical after `adj add`.)

## Why it matters

Two traps, one on each side.

**Reaching for the serializer** feels like the disciplined choice and quietly produces a
worse file. `toml::to_string(&cfg)` is faithful and valid — and strips the comments that
were the point. The user opens a two-line file with no hint of what else they can set or
what they still need to fill in. Knowing *when not to serialize* is the actual skill here:
struct-to-TOML for data you'll read back by machine, hand-rendered text for a file a human
edits next.

**Skipping the existence check** is the destructive one. `std::fs::write` truncates —
point it at a path that already holds a carefully-tuned manifest and the old contents are
gone, no prompt, no backup. The `!exists()` guard is what keeps a convenience feature from
eating the user's work.

One honest caveat: `exists()`-then-`write()` is check-then-act, so there's a hair-thin
window where the file could appear between the two calls. For an interactive command a
person runs at a shell, that window doesn't matter. If you needed it to matter — a
concurrent or hostile setting — the atomic form is
`std::fs::OpenOptions::new().create_new(true)`, which fails outright if the file already
exists rather than checking first. `adj add` doesn't need it; knowing the upgrade path
exists is the point.

## Related lessons

- **PR #41** is the sibling technique — it also builds a document with `format!` string
  templating, and teaches the raw-string-literal (`r#"…"#`) mechanics that make a
  multi-line template readable. This lesson is the *decision* that sits above that
  mechanism: why you hand-render a config at all instead of serializing a struct, plus the
  disk write. #41 is *how* to template; #75 is *when* (and how not to clobber).
- **PR #19** is the exact mirror: it reads `adjacent.toml` back in with
  `#[derive(Deserialize)]` and `Option` fields. #75 writes the file #19 parses — and #19's
  strict "missing `cmd` is an error" is what the `# TODO: set your dev command` placeholder
  is steering the user away from tripping.
- **PR #22** serializes DTOs to JSON *with* serde — because that output is consumed by
  `jq`, a machine, where a stable derived shape is exactly right. Put next to #75 they're
  the clean contrast: serialize for machines, hand-render for humans.
